# 云澜选址实验室（Atlas Site Lab）

零依赖的本地选址分析应用：合成城市 + 路网行程时间 + 网格需求 + 容量约束 + 新店分流/重叠 + 空间-时间隔离回测 + 版本化方案与可恢复任务。

> 全部需求、路网、门店、候选点与营业历史均为程序生成的虚构数据。**不调用任何商业地图、路径规划或真实交易系统**；输出为“到访人次/周”口径的方案比较，**不是收入、营收或成功率预测**。

---

## 快速开始

```bash
node scripts/seed.js      # 或 npm run seed：生成不可变输入快照与营业历史
node --test               # 或 npm test：20 项单元 + API 集成测试
node src/server.js        # 或 npm start：http://127.0.0.1:5173
node scripts/backtest.js  # 或 npm run backtest：CLI 回测，写入 data/backtests/latest.json
```

要求 Node.js ≥ 20，无第三方依赖、无需联网。服务只监听 `127.0.0.1`；`PORT` 与 `ATLAS_ROOT` 可覆盖端口与数据根目录（测试即用后者隔离）。

打开页面后：左侧勾选候选 → 右侧“当前方案”实时试算 → 拖拽地图上的候选点可改坐标（会重新试算）→“保存方案”固定输入版本 → 底部“已保存方案”可载入/对比/过期重算；“组合与前沿”跑候选组合搜索；“回测与检验”跑隔离回测；“任务”页可查看、重试、取消任务。

## 1. 输入版本：旧方案不会冒用新数据

每个输入文档（需求、路网、门店、候选、历史、模型参数）都按 **规范化 JSON 的 sha256** 生成版本号，例如 `net-cc72741827`。`versionKey` 把六个输入版本组合成 16 位短键。

- 保存方案时，记录 `inputVersions`、`inputVersionKey`、参数与**完整的评估结果**。
- 任一路网/需求修订会写入**新版本文件**并更新清单，而不是原地覆盖；`DatasetStore` 启动时重算哈希并与清单比对，不一致直接报错。
- `GET /api/scenarios` 会用当前版本比对每条方案，返回 `stale: true` 与逐项 `changedInputs`（旧值 → 新值）。**存下的评估结果原样保留**，页面提示“按新输入重算的预览”只是前台预览。
- 只有显式 `POST /api/scenarios/:id/relink` 才会重算并写回新版本；回测同理，`GET /api/backtest` 返回 `fresh:false` 并说明“输入或路网已修订”。
- 组合搜索结果同样带 `inputVersionKey`，`GET /api/optimizations/:id` 返回 `fresh` 标志。

修订入口（页面左栏按钮 / `POST /api/revisions/:preset`）：

| 预设 | 作用 |
| --- | --- |
| `demandEast` | 东北片区需求 +15% |
| `demandSouth` | 东南片区需求 −10% |
| `bridgeCongestion` | 关闭 1 行跨河桥（限速改为 0.01），跨河需绕行 |
| `parkPath` | 公园新增一条步行连接节点与两段路 |

修订返回 `revisionDiagnostics`（可达对数、行程时间中位数/均值、绕行比），用于发现“新增节点未连通”这类错误。

## 2. 路网距离与“直线近似”的解释

- 行程成本是**时间**，不是距离：路段按限速折算秒，每次转向加 6 秒，单行边只允许一个方向。
- 需求点与候选点先吸附到最近路网节点（平均 474 m），再按 4.8 km/h 计步行接驳时间。
- 中央公园挖空内部路口、澜川河仅 1/4/7 行架桥，因此存在真实绕行。全量 2520 个需求—目的地对：**平均路网 12.48 分钟，平均直线 8.86 分钟，平均绕行比 1.57×**；约 1.2% 的对属于“直线看似近、路网其实远”（直线 < 10 分钟而路网 > 15 分钟）。
- 若切换到直线模式，接口会显式标注这是 22 km/h 匀速 + 接驳的近似，仅用于敏感度对照，不作为主口径。

## 3. 需求、竞争与“不能逐点相加”

对每个需求点 `i`、目的地 `j`：

```
U_ij = size_j^alpha · appeal_j · exp(-beta · t_ij)
P_ij = U_ij / Σ_k U_ik        （t_ij > cutoff 的目的地直接不参与）
```

`size` 为营业面积，`appeal` 为格式/运营吸引力，`beta`、`alpha` 由回测拟合。**需求在同一需求点的所有目的地之间按概率分配**，不是各目的地各预测一份。

容量：目的地上限 `capacityVisitsPerWeek`。分配采用迭代“水位”法：先按概率分配；任何超过容量的目的地被钉在容量上、从活跃集中移除，剩余需求在其余目的地间重新归一化分配，直到没有新的触顶或需求耗尽。未满足部分单列为 `unmetVisits`，其中“超出 12 分钟圈层”的部分另见 `beyondCutoffVisits`，“容量回溢”部分另见 `capacityOverflowVisits`。

因此组合评估天然体现：

- **新店分走旧店需求**：同一批需求点在新旧店之间重新分配，`cannibalizedExistingVisits` 为旧店到访的减少量。
- **新店之间重叠**：`sharedVisitsBetweenNewStores` 是同一需求点同时被两家新店分到的期望人次。
- **真实增量** = 组合总到访 − 基线总到访；而“独立预测相加” = 各新店单独开店时的到访之和。示例（c-06 + c-18，第 25 期）：相加 1102.5、组合净增 634.9，重叠损失 467.6（42.4%），旧店被分流 5738.1；可达覆盖率 44.8% → 54.4%。页面用醒目提示说明这一差额。

## 4. 目标：覆盖 vs. 重叠

`POST /api/optimize` 枚举候选池（默认 23 选 k，k=1..6；超过 6000 组合时按单店增量预筛并明确提示“结果不再是全局最优”），每个组合计算：

- `accessCoverage`：8 分钟可达圈层覆盖的需求份额（加新店后覆盖增益有限，能暴露“重复布点”问题）
- `overlapShare` = 0.5 × 新店间共享占新店到访 + 0.5 × 旧店被分流占旧店基线（两个分量先各自归一化再平均，避免大基数吞掉小分量）
- `rentIndexTotal`：租金指数合计

输出 Pareto 前沿（覆盖↑ / 重叠↓ / 租金↓ 非支配解），再按用户权重做 min–max 归一化打分给出**一个**推荐。`goalConflict` 在“覆盖最高”和“重叠最低”不是同一组合（差距 > 1 个百分点）时为真，并提示权重会改变推荐；否则提示目标同向、权重影响有限。另给出前 20 组合的候选入选频率，作为稳健性参考。

## 5. 空间-时间隔离回测

训练：第 1–12 期；验证：第 13–24 期。5 个空间块由最远点初始化 + Lloyd 迭代得到，每次留出一个块：

- 训练只用训练期、且剔除最后 1 期（purge）；
- 与被留出需求点相距 900 m 以内的训练点一并剔除（spatial embargo）；
- beta、alpha 在网格上按训练 WAPE 选择，门店吸引力与月度因子只用训练样本拟合；
- 指标 WAPE / MAE / RMSE / bias，并给出每折的 beta/alpha、训练/验证单元数。

同时运行一次**随机单元切分**作为泄漏诊断（80% 训练）。当前合成数据上的结果：

| 指标 | 数值 |
| --- | --- |
| 隔离回测 WAPE | 13.5% |
| bias | −2.4% |
| 随机切分 WAPE | 14.3% |

随机切分允许同一需求点、相邻期同时进入训练与验证，是**不能**作为泛化证据的协议；本模型不含点位级参数，所以它在此数据上主要反映误差估计不稳定，而非必然“更好看”。报告文字明确说明这一点，也说明该分数只证明合成过程内部一致。

**营业变更检验**：s-02 于第 18 期关店后，邻近 20 个需求点只把其关前到访的 **64.9%** 转移给其他门店（s-05 距离 430 m），其余因容量与距离损失——用于检验模型是否错误地假设需求会 100% 平移。

## 6. 不确定性

方案评估可附带蒙特卡洛（默认 120 次）：需求点乘性误差 σ=0.10、门店吸引力 σ=0.12、beta σ=0.015，固定种子可复现。返回净增量的 P10/P50/P90 与“为正的概率”，并在前端注明这是**参数敏感性区间，不是收入置信区间**。

## 7. 页面与交互

- SVG 地图：公园/河道、按等级着色的路段、需求点大小映射需求量、门店/候选点标记；三个图层（重叠热度、8 分钟可达圈层、现有店分流）。
- 拖动候选标记改坐标（写入方案参数，参与重算与保存）；缩放/平移；“重置视图”。
- 方案对比条：多方案增量并排，过期方案带 ⚠。

## 9. 主要假设与限制

- 城市、人口、门店、容量、租金指数均为虚构；不存在“真实答案”，回测分数只衡量内部一致性。
- 距离是静态自由流时间：无实时路况、无公共交通、无分时段拥堵；绕行比 1.57× 是刻意加入的合成特征。
- 需求按网格点聚合，忽略点内空间分布；单点需求视为同质。
- Huff 模型不含品牌忠诚、出行链、跨区竞争等；吸引力主要来自格式与面积。
- 到访人次 ≠ 收入：没有客单价、毛利、租金绝对值，只有相对租金指数。
- 组合搜索在候选数大时依赖预筛，且只搜索固定开 k 店的组合；不处理多阶段扩张。
- 前端未在真实浏览器中做端到端自动化（环境无浏览器、无网络安装 Playwright）；已通过 API 集成测试、DOM id 交叉检查与静态资源探测验证。

## 10. 修订与 seed 的注意点

`node scripts/seed.js` **只补齐缺失文件**：如果已经存在（可能已被修订过的）`data/datasets/active/*.json`，它不会覆盖，也不会用新生成的文档重算清单——清单版本始终由磁盘上的当前文件推导。需要回到初始合成城市时用 `node scripts/seed.js --force`（会重建全部输入，此前的方案/回测会全部变“过期”）。
